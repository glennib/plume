# Targeting the DuckDB v2 C API from Rust

Research date: 2026-09-27.
Source inspected: `duckdb/duckdb` branch `v2.0-cyanoptera` (the default branch), HEAD `d8a1bd4f` (2026-09-25).
DuckDB v2.0 is in preview; GA is announced for fall 2026.

## Summary

DuckDB v2 ships a new, versioned C API with a stable ABI for loadable extensions.
It is specified declaratively in YAML and the C headers are generated from that spec.
A Rust extension can target it directly,
either through bindgen over the generated extension header or through a generator reading the YAML.
The C API does **not** expose parser or grammar extension,
see [the parser report](2026-09-27-duckdb-v2-parser-extensibility.md).

## The specification

- `api_spec/v2/` holds one directory per module (`function/`, `vector/`, `data_chunk/`, `logical_type/`,
  `connection/`, `sql_statement/`, `tokenizer/`, ...) plus `metadata.yaml`.
- `metadata.yaml`: `schema_version: "0.7"`, `versions: ["v2.0.0"]`, symbol prefix `duckdb_v2_`.
  Handles are suffixed `_handle`, callbacks `_fn`, aliases `_t`.
- Every symbol carries a lifecycle stack (`unstable` → `stable` → `deprecated` → `removed`), each entry dated and
  tagged with the release, e.g. `[ "stable", "v2.0.0", "2026-09-01" ]`.
- Headers are generated by [capigen](https://github.com/duckdb/capigen), pinned in `api_spec/pyproject.toml`:
  - `src/include/duckdb_v2.h`: the API for direct consumers linking `libduckdb`.
  - `src/include/duckdb_extension_v2.h`: the API for loadable extensions (function-pointer table plus indirection
    macros).
  - `src/include/duckdb/main/capi_v2/extension_api_v2.hpp`: the engine-side table.
- `api_spec/VERSIONING.md` documents the ABI rules (written for v1, and v2 follows the same scheme).

## Extension ABI

- The extension exports one symbol, `<name>_init_c_api_v2`, taking a single `duckdb_v2_extension_input` (defined in
  `api_spec/v2/extension/extension.yaml`):
  - `get_api(extension, "v2.0.0")` returns the function-pointer table for the requested API version,
    or NULL if this DuckDB cannot serve it.
    It is called once, before anything else.
    It is NULL for statically linked extensions.
  - `extension` identifies the loading extension.
    Functions, types, casts and replacement scans are registered through it (`*_create_with_extension`).
  - `context` is a borrowed client context with an active transaction, valid only during the entrypoint.
  - `err` is an error slot; setting a code on it fails the load.
- The function-pointer table is grouped into contiguous bands by the version a function was **stabilised** in.
  Targeting a version truncates the struct to the slots that version shipped,
  so a build against `v2.0.0` stable loads on any later DuckDB that still serves that prefix.
- Unstable symbols are opt-in (`DUCKDB_API_ALLOW_UNSTABLE`), live at the end of the table,
  and tie the binary to the newest version.
  Unstable and an older target are mutually exclusive.

## Surface relevant to this project

Available through the stable C API:

- Scalar, aggregate, table, cast and copy functions (`api_spec/v2/function/`), with named parameters and varargs.
- Custom logical types (`logical_type/custom_type.yaml`), useful for a `CHART` type alias over `BLOB`/`VARCHAR`.
- Direct vector buffer access, data chunks, values, Arrow interop.
- Parsing and tokenizing SQL in the context of loaded grammar extensions (`sql_statement`, `tokenizer`), but not
  extending the grammar.

Gaps observed:

- Table functions take only scalar arguments; there are no table-input (in-out) table functions.
- Executing a query needs a `connection` handle.
  Callbacks such as table-function bind receive a `context`,
  and from the spec names alone no path from a `context` or `extension` handle to a `connection` was found.
  Not verified in depth.

Aggregates avoid both gaps: an aggregate consumes the rows of an arbitrary subquery without any nested execution.

## Rust ecosystem status

- `duckdb-rs` PR [#855](https://github.com/duckdb/duckdb-rs/pull/855), merged 2026-09-14:
  `libduckdb-sys` gains a `capi-v2` feature generating `duckdb_v2.h` bindings into `libduckdb_sys::v2`,
  and a new `duckdb-neo` wrapper crate targets the v2 API.
  Both target a v2 alpha and are marked unstable.
  Whether they support v2 **loadable extensions**
  (entrypoint macro, `duckdb_extension_v2.h` indirection) was not confirmed.
- `duckdb-rs` issue [#875](https://github.com/duckdb/duckdb-rs/issues/875):
  request to expose the C++ API to Rust extensions.
  Open, no maintainer response.
- The DuckDB v2 announcement mentions forthcoming official Rust bindings for extension authors, without detail.

## Options for the -sys layer

1. **bindgen over `duckdb_extension_v2.h`** with `DUCKDB_API_VERSION_*` pinned to 2.0.0.
   The fastest route.
   The indirection macros do not survive bindgen,
   so the Rust side stores the table returned by `get_api` and calls through it.
2. **Generate from the YAML.**
   The spec carries ownership (`kind: OUT`, `role: constructor`, `belongs_to`), lifecycle and docs,
   which is enough to generate both the raw table and much of a safe wrapper.
3. **Depend on `libduckdb-sys` with `capi-v2`.**
   Least code, but ties us to duckdb-rs release cadence and its alpha pin.
