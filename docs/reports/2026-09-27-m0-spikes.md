# M0 spikes: the v2 C API from Rust, and a footer without extension-ci-tools

Research date: 2026-09-27.
Sources inspected:

- `duckdb/duckdb` branch `v2.0-cyanoptera`, local shallow clone at HEAD `3f9f0a17` (2026-09-27):
  `src/include/duckdb_extension_v2.h`, `api_spec/v2/`, `src/main/capi/v2/`.
- Preview binaries: the staged CLI `v2.0.0-alpha43385` (source id `ca15f79c32`) with its shared-libs tarball,
  the nightly CLI `v2.0.0-alpha43546` (`d8a1bd4f4f`), and the Python wheel `duckdb==2.0.0.dev2609250715`.
- `duckdb/duckdb-sqllogictest-python` at `2ac8dbc0` (the commit extension-ci-tools installs) and `main` at `66b0687f`.
- `duckdb/extension-ci-tools` `main` at `20bad04`: `scripts/append_extension_metadata.py`,
  `makefiles/c_api_extensions/base.Makefile`.
- The spike code itself: `crates/duckers-sys` (bindgen over the vendored header) and `crates/duckers`
  (`src/capi/`, the safe layer, and `src/spike.rs`, the spike functions), built with Rust 1.98.1 and bindgen 0.73.2.

This report follows [v2 preview builds and C API details](2026-09-27-duckdb-v2-preview-and-capi-details.md),
which did the same checks from C. "Verified" means run against a preview binary or read directly in the source.
"Inferred" means concluded from the spec or source without running it.

## Summary

- A Rust `cdylib` exporting `duckers_init_c_api_v2`,
  calling DuckDB only through the function-pointer table that `get_api` returns, loads into the staged `alpha43385` CLI,
  the nightly `alpha43546` CLI and the wheel with `-unsigned`.
  The table is bindgen output over the vendored `duckdb_extension_v2.h`; no DuckDB symbol is linked.
- **Named parameters work on scalar functions**, which closes the plan's open question.
  Defaults, out-of-order names, skipped optional parameters,
  non-constant named arguments and the dot-call syntax all bind,
  and exec always sees every parameter as a positional vector.
- An order-independent aggregate with `ANY` and named parameters binds, type-checks in bind, and runs ungrouped,
  grouped, over 3,000,000 rows with the default thread count, and over an empty input.
  `ORDER BY` inside the call is dropped as the earlier report found.
  **`OVER ()` still segfaults with the order-independence property set**; the property only fixes `ORDER BY`.
- A custom type over `BLOB` with `VARCHAR` and `BLOB` casts both ways behaves as the C probe did.
  A string literal cast (`'abc'::SPIKE_CHART`) bypasses a registered `BLOB → SPIKE_CHART` cast.
- The footer is 512 bytes appended by a short standard-library Python script; the Makefile runs it.
  The 22-byte WebAssembly prefix that extension-ci-tools writes is not needed.
- Three gotchas the C probe did not hit: every load must call `get_api` (a second database in the same process fails
  with a fatal error otherwise), `vector_set_null` rejects every row of a scalar result vector, and an `ANY` parameter
  cannot have a NULL default of type `ANY`.
- The staged `alpha43385` build ships CLIs for Linux, macOS and Windows on both architectures, and the wheel has the
  same spread, so CI can test on all three systems.

## Spike 1: the C API from Rust

### Bindings (verified)

- `crates/duckers-sys/vendor/` holds `duckdb_v2.h` and `duckdb_extension_v2.h` from the staged shared-libs tarball
  (`vendor/VERSION` records the URL and checksum).
  Both are byte-identical to `src/include/` at `v2.0-cyanoptera` HEAD `3f9f0a17`, two days later.
- bindgen runs with `allowlist_type("duckdb_.*|DUCKDB_.*|idx_t")`, `allowlist_var("DUCKDB_.*")`,
  constant-style enums and no functions.
  The `#define duckdb_v2_x duckdb_ext_api.duckdb_v2_x` indirection macros produce nothing, as expected,
  and the free function declarations in `duckdb_v2.h` are left out because a loadable extension cannot link them.
  The output is 9,168 lines, checked in as `src/bindings.rs`; `make bindings` regenerates it
  (feature `generate-bindings`), so a normal build needs no libclang.
- The table `duckdb_ext_api_v2` comes out
  as a `#[derive(Copy, Clone, Default)]` struct of `Option<unsafe extern "C" fn(...)>` fields.
  `init_api` copies it into a `OnceLock` as the C macro `DUCKDB_EXTENSION_API_INIT` does,
  and `ffi!(name(args))` calls a slot.
- The table struct in the header has no `#if` inside it, so neither `DUCKDB_V2_API_ALLOW_UNSTABLE` nor
  `ALLOW_DEPRECATED` changes its layout.
- C enums become `c_uint` type aliases.
  MSVC makes them `int`; the values are small and the two share an ABI,
  so one checked-in file serves every platform (inferred).
  The generated layout assertions assume 64-bit pointers, which all target platforms have.

### Entrypoint and loading (verified)

- The loader looks up `<file stem>_init_c_api_v2` when the footer has ABI `C_STRUCT` and a `v2.x.y` version.
  Renaming the file to `other_name.duckdb_extension` fails with 'did not contain function "other_name_init_c_api_v2"'.
- A Rust `#[unsafe(no_mangle)] pub unsafe extern "C" fn duckers_init_c_api_v2(input: *mut duckdb_v2_extension_input)`
  in a `cdylib` is the only dynamic symbol the library exports (`nm -D --defined-only`).
- **`get_api` must run on every load.**
  With the table cached after the first load,
  a second `duckdb.connect()` in the same Python process failed with "FATAL Error:
  Extension ... did not initialize the C API struct ... must call DUCKDB_EXTENSION_API_INIT before anything else",
  and the process was left unusable.
  Calling `get_api` each time fixes it; the table it returns is the same.
  Three connections in one process and a repeated `LOAD` on one connection then work.
- Errors in the entrypoint, reported through `input.err`, fail the load with
  "An error was thrown during initialization of the extension '...': <text>".
- Callbacks are `unsafe extern "C" fn` trampolines that run the Rust body under `catch_unwind` and write errors
  and panics into the callback's error slot with `error_info_set_code` and `error_info_set_text`.
  The code picks the exception class: `ERROR_QUERY_BINDER` renders as "Binder Error: ...",
  `ERROR_TYPE_CONVERSION` as "Conversion Error: ...".

### Scalar functions with named parameters (verified)

`spike_join(x BIGINT, sep VARCHAR := ',', times BIGINT := 2) -> VARCHAR`,
registered through `function_signature_add_parameter` with a default value for `sep` and `times`, and a bind callback:

| Call | Result |
| --- | --- |
| `spike_join(7)` | `7,7` |
| `spike_join(7, '\|')` | `7\|7` |
| `spike_join(7, times := 3)` | `7,7,7` (skips `sep`) |
| `spike_join(x := 7, sep := '-', times := 1)` | `7` |
| `spike_join(times := 2, x := 5)` | `5,5` (names in any order) |
| `(i).spike_join(times := i) FROM range(4)` | `''`, `1`, `2,2`, `3,3,3` (dot call, non-constant named argument, `SEQUENCE` input) |
| `spike_join(i, sep := s)` over rows with NULLs | NULL where an argument is NULL |
| `spike_join(7, bogus := 1)` | Binder Error listing `spike_join(x BIGINT, sep VARCHAR := ,, times BIGINT := 2) -> VARCHAR` |
| `spike_join(sep := '\|', 5)` | Binder Error: "Positional argument '5' cannot follow named arguments in function call." |
| `spike_join(7, '\|', 3, 4)` | Binder Error, no match |

- Bind and exec both see three arguments in every call: the defaults are filled in before bind, in declaration order.
- The default value's text in the candidate list is not quoted (`sep VARCHAR := ,`), which reads oddly for string
  defaults but is DuckDB's rendering.
- Under the default NULL handling, rows with a NULL argument still reach exec; the callback writes NULL for them.
  Only all-constant NULL arguments are folded (`spike_join(NULL)` is NULL).

### Aggregates with `ANY` and named parameters (verified)

`spike_agg(x ANY, y ANY, label VARCHAR := 'none', key ANY := NULL::VARCHAR) -> VARCHAR`, order-independent,
with a bind callback that rejects non-numeric `x` and `y`:

- `spike_agg('a', 1)` fails at bind with "Binder Error: spike_agg: x must be numeric, got VARCHAR", the message the
  bind callback wrote.
- Bind sees four argument types, e.g. `(BIGINT, DOUBLE, VARCHAR, VARCHAR)`, defaults included.
  A constant `label` folds with `aggregate_function_bind_get_arg_value`; a column
  (`label := s`) does not fold and arrives per row in update.
- `key := i % 2` binds with type `BIGINT`; without it, the default arrives as a `VARCHAR` NULL.
- NULL rows reach update (the default NULL handling does not filter aggregate input): three rows with one NULL in each
  of two rows counted `rows=1 skipped=2`.
- `GROUP BY` gives one state per group; 3,000,000 rows ungrouped and in 1,000 groups aggregated correctly with
  combine running across worker threads.
- An empty input finalizes a state that update never touched.
  The wrapper allocates states lazily
  (a null pointer in DuckDB's state slot until the first row),
  so finalize creates an empty state for such slots and destroy frees it.
- `spike_agg(i, i ORDER BY i DESC)` returns the plain result; the `ORDER BY` is dropped as reported.
- **`spike_agg(i, i) OVER ()` segfaults** (exit 139) even with `FUNCTION_PROPERTY_AGG_ORDER_DEPENDENT_NO`.
  This is duckdb#26109's second trigger: the window operator passes a constant state vector with `count > 1`,
  which the update callback cannot detect.
  The plan's statement that `OVER ()` is unsupported until the fix lands stands; the order property does not help.

### Custom type over `BLOB` (verified)

`SPIKE_CHART` over `BLOB`, with casts `SPIKE_CHART → VARCHAR`
(a summary), `SPIKE_CHART → BLOB` (copy) and `BLOB → SPIKE_CHART` (copy after checking a 3-byte prefix):

- `typeof(spike_chart('hello'))` is `SPIKE_CHART`; the box renderer and `-json` print the cast's summary
  (`SPIKE_CHART(8 bytes)`); `::BLOB` gives the bytes back.
- Values longer than 12 bytes go out of line through `vector_get_arena` and `arena_allocate`.
- `'xyz'::BLOB::SPIKE_CHART` raises the cast's error ("Conversion Error: not a SPIKE_CHART value");
  `TRY_CAST` of the same gives NULL, since the callback sees `DUCKDB_V2_CAST_MODE_TRY` and writes NULL instead of
  failing.
- **`'abc'::SPIKE_CHART` does not go through the registered `BLOB → SPIKE_CHART` cast**:
  it produces a 3-byte value without the prefix the cast checks.
  A string literal casts to the custom type through the base type directly.
  Anything reading a custom-type value must therefore handle bytes that were never validated.
- `CREATE TABLE t(c SPIKE_CHART)`, inserts from the constructor, and the dot call `('x').spike_chart()` work.
- The wheel returns the raw `bytes` for a `SPIKE_CHART` column, as the earlier report found.

### Vectors (verified)

- `vector_get_view` gives data, an optional validity mask and an optional selection vector for flat,
  constant and dictionary vectors (`src/main/capi/v2/capi_v2_vector.cpp:99-160`).
  Reading through the selection vector handles all three without flattening; only `VECTOR_TYPE_OTHER`
  (`range()`'s `SEQUENCE`, FSST) needs `vector_flatten` first.
  The same reader serves scalar exec, aggregate update and casts.
- **`vector_set_null` fails on scalar result vectors** with "row out of range in duckdb_v2_vector_set_null":
  it bounds-checks against `vector_get_size`, and a result vector's size is not set during exec.
  Clearing the row's bit through `vector_flat_get_validity_mutable` works.
  For STRUCT or ARRAY results the nested children would need clearing too (spec); duckers returns neither.
- `value_create_null_with_context` with an `ANY` type fails with "type cannot be ANY", and
  `context_create_type_from_id` refuses `SQLNULL`, so an `ANY` parameter's NULL default has to be a typed NULL.

## Spike 3: the footer without extension-ci-tools (verified)

- `scripts/append_footer.py` (standard library only) copies the library and appends eight 32-byte fields
  and a 256-byte zero signature: three unused fields, the ABI (`C_STRUCT`), the extension version (`v0.1.0`),
  the C API version (`v2.0.0`), the platform, and the magic `"4"`.
  It maps Rust target triples to DuckDB platforms
  (`x86_64-unknown-linux-gnu` → `linux_amd64`, `aarch64-apple-darwin` → `osx_arm64`,
  `x86_64-pc-windows-msvc` → `windows_amd64`, ...).
- `make` (`build_debug` then `footer_debug`) writes `build/debug/duckers.duckdb_extension`;
  `make release` the optimised one (618 kB).
  Both load with `-unsigned` into the staged CLI, the nightly CLI and the wheel.
- The extension-ci-tools script also writes a 22-byte WebAssembly custom-section header before the fields.
  The native loader reads only the last 512 bytes, and the file loads without it.
  A Wasm build would need it back (inferred).
- Failure modes, each checked by writing a deliberately wrong footer:

  | Footer | Load result |
  | --- | --- |
  | none | "The metadata at the end of the file is invalid" |
  | platform `osx_arm64` on Linux | "built for the platform 'osx_arm64', but we can only load extensions built for platform 'linux_amd64'" |
  | C API `v2.1.0` | "built for DuckDB C API version 'v2.1.0', but we can only load extensions built for DuckDB C API 'v2.0.0' and lower" |
  | C API `v1.2.0` | looks up the v1 entrypoint `duckers_init_c_api` and fails |
  | correct footer, no `-unsigned` | "signature is either missing or invalid" |

- The library file name differs per platform (`libduckers.so`, `libduckers.dylib`, `duckers.dll`); the Makefile picks
  it from the target triple and always writes `duckers.duckdb_extension`, whose stem the entrypoint name depends on.

## Tooling found along the way (verified)

- The staged build is pinnable by URL:
  `duckdb-staging.duckdb.org/ca15f79c32/v2.0.0-alpha43385/duckdb/duckdb/github_release/` has
  `duckdb-cli-{linux-amd64,linux-arm64,osx-amd64,osx-arm64,osx-universal,windows-amd64,windows-arm64}.tar.gz` (the
  Windows archives hold `duckdb.exe`) and `duckdb-shared-libs-{linux-amd64,osx-universal,windows-amd64}.tar.gz`.
  The nightly URL on `artifacts.duckdb.org` redirects to a GitHub Actions artifact that is replaced daily.
- The wheel `2.0.0.dev2609250715` has builds for CPython 3.11 and later on manylinux x86_64 and aarch64, macOS
  (x86_64, arm64, universal2) and Windows (amd64, arm64).
- DuckDB's Python sqllogictest runner is `duckdb-sqllogictest-python`.
  Its `main` (`66b0687f`) is now a library without a `__main__`; the commit extension-ci-tools pins, `2ac8dbc0`
  (the head of its PR #11), has the runner.
  `python -m duckdb_sqllogictest --test-dir test/sql --external-extension build/debug/duckers.duckdb_extension` runs
  against the v2 wheel, honours `require duckers`, and exits non-zero on a mismatch.
